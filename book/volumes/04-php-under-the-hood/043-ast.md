# Chapter 43 — AST

## Why This Matters

An Abstract Syntax Tree (AST) is the first representation in this pipeline that looks like a program rather than a stream. It records operators, operands, declarations, statements, and nesting while discarding details that do not determine execution, such as most whitespace. This makes it the natural meeting point for a compiler, static analyzer, refactoring tool, and language server.

It also prevents a common category error: an AST is not source text and not executable code. Walking an AST can tell a tool that a function contains a call to `query()`. It does not tell the tool what the database returns or whether a branch will be reached.

## Mental Model

```text
source:  $total = (10 + 5) * 2;

AST:
assignment
├── variable: total
└── multiply
    ├── add
    │   ├── integer: 10
    │   └── integer: 5
    └── integer: 2
```

The tree captures grammatical relationships. Parentheses may not need their own runtime node when they only force grouping; their effect is visible in the tree shape. Comments may be preserved separately for tooling or documentation, but they are not generally executable expressions.

## Core Concept

AST nodes typically have a kind, attributes, source line, and child nodes. Current php-src defines these internal structures in [Zend/zend_ast.h](https://github.com/php/php-src/blob/master/Zend/zend_ast.h). The exact fields and node kinds are version-sensitive. Use this model to reason about the compiler, not as a promise that a particular offset or enum value is stable.

An AST separates two jobs:

```text
parser:   tokens → grammatical nodes
compiler: nodes → executable structures
analyzer:  nodes → facts, warnings, and inferred relationships
```

The same tree can support different consumers. A compiler may need a node’s line number for opcode metadata. A formatter may need token trivia that the core AST does not retain. A static analyzer may add its own symbol and type facts rather than mutate the engine’s tree.

## How It Works

The [Abstract Syntax Tree RFC](https://wiki.php.net/rfc/abstract_syntax_tree) records the PHP 7 change from a parser that emitted opcodes directly to a parser that first constructs an AST. The separation allows the compiler to make multiple passes or choose compilation strategies without forcing every parser production to know how machine-independent VM instructions should be emitted.

Consider a function:

```php
<?php

function discountedTotal(int $quantity, int $unitPrice, int $discount): int
{
    $gross = $quantity * $unitPrice;

    return $gross - $discount;
}
```

The AST has a function declaration node containing parameter declaration nodes and a statement list. The list contains an assignment whose right side is a multiplication expression, followed by a return expression. The compiler later chooses how to represent local variables, temporaries, return paths, and type checks in the op array.

An AST is usually “abstract” because it omits distinctions that do not matter to the grammar’s meaning. It is not a lossless source document. If a tool must preserve comments, exact quote style, alignment, or original parentheses, it needs tokens, a concrete syntax tree, or a source map alongside the AST.

## What PHP Does

PHP itself does not provide a general, stable built-in function that returns the engine’s internal AST for arbitrary source as an application API. The optional `ext/ast` extension is a separate tool with its own versioned AST API; if you use it, pin and test the extension version with the PHP versions you support. Do not confuse its public node objects with Zend’s private `zend_ast` structures.

For most application developers, the AST is observable indirectly through syntax behavior, static analysis diagnostics, and opcode/debug tooling. For engine contributors, the source headers and compiler code are the authoritative implementation references.

## What Zend Does

The parser’s semantic values can be AST nodes. The compiler entry point `zend_compile_ast()` is declared in [Zend/zend_compile.h](https://github.com/php/php-src/blob/master/Zend/zend_compile.h), and compiler traversal is implemented primarily in [Zend/zend_compile.c](https://github.com/php/php-src/blob/master/Zend/zend_compile.c). These links point to the moving `master` branch; read a tag or branch matching the PHP binary when investigating an exact production behavior.

The engine allocates AST nodes during compilation and releases them after they have served the compiler, subject to the implementation’s ownership and arena rules. The resulting op array, literals, function metadata, and class metadata have a different lifetime and purpose. “The AST is cached” is therefore not a safe generic statement; OPcache caching is a separate mechanism with its own representation and compatibility rules.

## Minimal Example

A small expression can be represented as:

```text
AST_ADD
├── AST_VAR("left")
└── AST_MUL
    ├── AST_CONST(2)
    └── AST_CONST(3)
```

This tree says multiplication is nested under addition. It does not say whether `left` is defined, what type it has, or whether evaluating it has side effects through overloaded object behavior.

## Practical Example: Tree Shape and Side Effects

These expressions are not interchangeable:

```php
<?php

$value = readValue() + fallback();
$value = readValue() ?? fallback();
```

The AST distinguishes an addition node from a null-coalescing node. The compiler and VM preserve different evaluation and short-circuit rules. An AST walker that merely lists function-call descendants may report both calls but still miss the important fact that `fallback()` is conditional in the second tree.

This is why static analysis needs more than node names. It must understand evaluation order, control-flow edges, scopes, and possible types.

## Bad Example

```php
// A simplistic “security analyzer” that flags every string named query.
foreach ($nodes as $node) {
    if ($node->name === 'query') {
        report('SQL injection');
    }
}
```

A call name is not a data-flow proof. The receiver, arguments, string construction, taint sources, escaping, query API, and execution path all matter. AST structure is a foundation, not a complete security analysis.

## Better Example

For a narrow rule, define the claim precisely:

```text
find calls to a known database API
    → inspect whether the query argument is a literal or parameterized expression
    → follow local data flow where supported
    → report uncertainty instead of claiming proof
```

Use the AST to locate structure, then add symbol resolution and data-flow facts. Keep the analysis version-aware because new syntax can introduce new node shapes or call forms.

## Edge Cases

- Parentheses affect tree structure but may not survive as a dedicated node.
- Source line numbers can be attached to nodes, but one node can correspond to a range of source text.
- Namespaces and imports affect name resolution beyond the raw identifier node.
- Constant expressions may be represented in the AST and later folded or validated by compilation.
- Closures, arrow functions, generators, fibers, attributes, and anonymous classes introduce nested scopes or metadata.
- An AST does not automatically encode runtime values, autoloading results, database state, or side effects.
- AST node kinds and attributes are not a cross-version serialization format unless a tool defines and migrates its own schema.

## Performance

AST construction allocates nodes proportional to source complexity. Holding trees for thousands of files can consume considerable memory, especially when a tool also retains source text, tokens, symbol tables, and inferred types. Stream files through an analyzer when possible, cache normalized facts rather than entire trees when appropriate, and measure peak memory rather than only elapsed time.

## Security

Parsing untrusted source into an AST is safer than executing it, but the parser and analyzer still consume attacker-controlled input. Set size and nesting limits in services that accept source, avoid unsafe deserialization of AST objects, and do not treat a successful parse as permission to compile or run code. If a formatter writes transformed code, validate the output before it enters a deployment path.

## Testing

AST-consuming tools benefit from:

1. Golden fixtures for representative syntax and expected normalized trees.
2. Round-trip tests when the tool prints source again.
3. Negative tests for malformed syntax and unsupported PHP versions.
4. Property tests asserting that harmless whitespace changes do not alter semantic tree shape.
5. Regression tests for evaluation order and short-circuit nodes.

Avoid asserting private Zend node integers in application tests. If you use `ext/ast`, test against its documented versioned AST API and pin the extension in CI.

## Common Mistakes

- Calling the AST a lossless parse tree.
- Assuming the core engine AST is a stable public API.
- Treating a node’s text as its resolved symbol.
- Ignoring scope and evaluation order.
- Keeping every tree in memory without a peak-memory budget.
- Assuming an AST walker can prove security properties without data-flow analysis.

## Senior Engineer Thinking

Ask what information each representation intentionally forgets. The AST forgets some lexical trivia to make meaning easier to process. That is a benefit for a compiler and a problem for a formatter. Good tools choose a representation based on the claim they must make, and they make uncertainty visible when the tree alone cannot support the claim.

## Exercises

1. Draw ASTs for `$a + $b * $c` and `($a + $b) * $c`.
2. Explain the structural difference between `read() + fallback()` and `read() ?? fallback()`.
3. Build a fixture catalog for a tool that finds calls to a named API, including namespaces, methods, closures, and dynamic calls.
4. If `ext/ast` is available in a development environment, compare its output across two supported PHP versions and document the compatibility boundary.

## Review Questions

1. Why is an AST more useful than tokens for nested structure?
2. What information might a core AST omit that a formatter needs?
3. Why does an AST node for a function call not prove the call will happen?
4. How did the PHP 7 AST change improve compiler/parser separation?
5. Why should internal AST node kinds not be persisted as a long-lived application format?

## Summary

The AST is a structured, abstract representation between parsing and compilation. It records grammatical meaning and nesting while omitting some source trivia. PHP 7 introduced this separation deliberately; current Zend structures and node kinds remain implementation-specific. Use ASTs for structural tooling, but add scope, symbol, type, and data-flow analysis before making stronger claims.
