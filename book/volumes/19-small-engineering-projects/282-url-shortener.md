# Chapter 282 — URL Shortener

## Why This Matters

A URL shortener maps a compact public code to a longer destination. The first version can be built in an afternoon, but its contracts are surprisingly broad: codes must remain unique, redirects must be fast, deleted links must not resurrect, owners must not read one another’s private links, and analytics must not turn visitors into an unbounded identity database.

The shortener also demonstrates an important security distinction. The service stores and returns a destination; it does not automatically fetch that destination. A preview worker, malware scanner, or metadata crawler may fetch it later, which creates SSRF and abuse concerns that a simple HTTP redirect does not solve.

## Define the Product Contract

Start with explicit behavior:

~~~text
create: authenticated owner submits an absolute http or https URL
code: 8-character random base62 code, generated by the service
visibility: public redirect; owner-only management
redirect: temporary redirect while policy and caching are evaluated
expiry: optional UTC instant; expired links behave as not found
deletion: owner can disable; disabled links never redirect
retry: client may repeat creation with an idempotency key
analytics: aggregate counts with bounded retention and minimal data
abuse: rate-limit creation, validate destinations, and support reports
~~~

This contract intentionally does not promise that every URL is safe, permanent, or reachable. A short code is an identifier, not proof that the destination is trustworthy. The service needs an abuse process and a way to disable a link after creation.

## Validate the Destination

Parse the URL with a standards-aware library or carefully tested parser. Require an absolute URL, an allowed scheme, a valid host, no userinfo credentials, and a product policy for ports, fragments, and internationalized names. Reject `javascript:`, `data:`, `file:`, and other schemes unless there is a compelling, reviewed reason to support them.

Do not fetch the URL in the create request merely to “verify” it. That turns user input into a server-side network request and creates SSRF risk. If a later preview or scanning worker fetches destinations, it needs the SSRF controls from Chapter 147: named egress policy, DNS and redirect revalidation, private-range blocking, timeouts, response-size limits, and no access to instance metadata or internal services.

Canonicalization is a policy choice. Lowercasing a host is usually safe, while changing path encoding, query ordering, default ports, or percent escapes can change application meaning. Store the submitted destination and, if deduplication is offered, use a separately defined canonicalization algorithm with tests. Never claim that two URLs are equivalent merely because a string normalizer made them look alike.

## Generate Codes and Handle Collisions

Sequential integer IDs encoded as base62 are compact but enumerable. They can expose creation volume and make private or recently created links easy to guess. Random codes reduce prediction when generated with a cryptographically secure source, but uniqueness still comes from a database constraint and retry loop.

~~~php
<?php

declare(strict_types=1);

function randomBase62(int $length): string
{
    if ($length < 1) {
        throw new InvalidArgumentException('Code length must be positive');
    }

    $alphabet = '0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ';
    $last = strlen($alphabet) - 1;
    $code = '';

    for ($i = 0; $i < $length; $i++) {
        $code .= $alphabet[random_int(0, $last)];
    }

    return $code;
}
~~~

For eight base62 characters there are `62^8` possible codes, roughly 2.18 × 10¹⁴. That is a large space, not a proof that collisions cannot occur. At high occupancy, collision probability rises; measure the retry rate and choose length from expected population, privacy, and operational limits. A unique index on `code` is the authority. If insertion loses a uniqueness race, generate a new code and retry a bounded number of times.

Do not use a predictable pseudo-random generator, timestamps alone, or a hash of a secret that is reused without an analyzed collision and disclosure policy. If codes are tenant-scoped, state whether the same code may point to different destinations in different tenants; public redirect routing usually requires globally unique codes.

## Make Creation Idempotent

A browser or client can time out after the database commits. Retrying without an idempotency contract creates multiple codes for one user action. Accept an idempotency key scoped to the authenticated owner and operation, store a request fingerprint, and return the original result for an identical retry. A reused key with a different destination must fail.

Creation needs two uniqueness decisions:

* `idempotency(owner_id, key)` identifies a command retry;
* `code` identifies the public resource.

They are not interchangeable. A URL may intentionally receive several different codes, while a command key must not silently create a new resource after a timeout. Chapter 141 and Chapter 281 cover idempotency and admission-control boundaries.

## Persist the Mapping

A minimal record contains:

| Field | Purpose |
| --- | --- |
| `code` | public lookup key, unique and immutable |
| `destination` | exact stored URL or reviewed canonical form |
| `owner_id` | management authorization |
| `created_at` | audit and retention |
| `expires_at` | optional UTC expiry |
| `disabled_at` | revocation without destructive deletion |
| `policy_version` | explains validation behavior |
| `idempotency_scope` and `idempotency_key` | command-retry identity |
| `request_fingerprint` | changed-payload detection |

Use a database constraint for uniqueness and indexes that match the read path. The redirect query should fetch one active record by `code`; management queries should use `owner_id` and creation time. An index improves lookup but does not replace authorization or the active-state predicate. Keep the idempotency record atomically with the mapping creation, or in a separate table with a unique `(owner_id, operation, idempotency_key)` constraint and the resulting mapping ID; a fingerprint alone cannot return the original result or enforce the key.

Keep disabled records long enough to prevent accidental reuse and to support audit or abuse investigations. Reusing a deleted code can cause old browser caches, printed material, or analytics references to reach a different destination. If reuse is ever allowed, document the cache and privacy consequences.

## Design the Redirect

The redirect handler should:

1. parse and bound the code from the path;
2. look up one record by its unique code;
3. reject disabled or expired records without revealing management data;
4. record a bounded click event or enqueue one without delaying the redirect;
5. return a redirect response with the stored destination.

Choose status semantics deliberately. `302 Found` or `307 Temporary Redirect` communicates that the mapping may change; `307` preserves the method, while `302` has broader historical browser behavior. A permanent `301` or `308` can be cached for a long time and makes later disablement or destination changes harder. The product must decide whether redirecting non-GET methods is allowed; a shortener intended for links should reject or narrowly handle methods it does not need.

Do not concatenate user input into an HTML response without context-specific escaping. A `Location` header is not a license to accept control characters or malformed values. Validate at creation, store safely, and use the framework’s response API to prevent header injection.

## Cache Without Losing Control

Redirects are cacheable behavior, but cache policy must match expiry and revocation. A long public cache can continue redirecting after an owner disables a link. A private management response must not be stored in a shared cache. Include appropriate cache directives and decide whether disabled/expired responses are briefly cacheable.

If the mapping is cached in Redis or an in-process cache, invalidate or version it on disable. A cache hit must still respect the active policy, expiry, and tenant/public visibility. Cache stampede protection may help for hot links, but it does not change the database’s ownership or revocation authority.

Hot links can create a different bottleneck: the database may be quiet while the edge, cache, analytics queue, or provider becomes saturated. Measure redirect latency and click-event loss separately. Analytics should be best-effort only if the product accepts missing counts; never delay a security or disablement decision on an optional counter.

## Analytics and Privacy

Avoid storing every raw IP address and user agent forever. Define the purpose, retention, aggregation, access control, and deletion behavior before adding analytics. Useful bounded signals include total clicks, time bucket, country or coarse network class when justified, and referrer category after privacy review. A unique visitor count is a policy-heavy estimate, not a free column.

The redirect path should have a bounded queue or sampling policy. If the queue is full, choose whether to drop analytics, shed redirect traffic, or apply a separate quota. Do not let a best-effort click counter become a reason to fail all redirects unless that is explicitly the business contract.

## Abuse and Ownership

The shortener can be used for phishing, malware distribution, spam, and bypassing reputation filters. Rate-limit creation and administrative operations using the identity and cost model from Chapter 281. Add destination reputation checks or review workflows only with a clearly bounded network and provider contract.

Authorization applies to create, list, inspect analytics, disable, and report actions. A public visitor may resolve a code without learning the owner’s identity or management metadata. An owner may manage only their own links unless an explicit administrative capability permits more. Apply the same rules to API, web, CLI, support, and abuse-repair paths.

## Tests That Matter

Test the pure and persistent boundaries:

* valid HTTP and HTTPS URLs are accepted;
* unsupported schemes, credentials, malformed hosts, and control characters are rejected;
* codes have the promised alphabet and length;
* a forced collision retries and a uniqueness race does not overwrite another mapping;
* identical idempotent creation returns the original code;
* a changed request under the same key is rejected;
* disabled and expired links do not redirect;
* adjacent codes remain independent;
* unauthorized management and analytics access is denied;
* redirect status, `Location`, and cache headers match policy;
* analytics failure does not violate the redirect contract when it is best-effort;
* cache invalidation prevents a disabled link from continuing indefinitely;
* concurrent creation and disablement have a defined result;
* rate limits protect creation without making public resolution unavailable.

Use a real database integration test for unique-code races, idempotency uniqueness, transaction behavior, and expiry queries. Use a cache and queue integration test for invalidation and bounded analytics. A unit test for `randomBase62()` cannot prove entropy, collision behavior, or database correctness.

## Rollout and Recovery

Deploy the creation API behind a feature flag, create records with the new schema, and keep redirect behavior independent from analytics. If the code format or destination policy changes, version the policy and preserve old records under their original interpretation. A rollback must still resolve existing codes and honor disabled/expired state.

If a cache contains an old destination after disablement, invalidate it or use a versioned lookup before serving. If analytics events are duplicated during queue replay, deduplicate by click-event identity or accept an explicitly approximate aggregate. Never restore a previous artifact that interprets a code as a different resource after mappings have been published.

## Common Mistakes

* Encoding sequential IDs and calling the result unguessable.
* Treating random generation as uniqueness instead of using a database constraint.
* Creating a new code after a client timeout without an idempotency contract.
* Reusing a code after deletion while old caches or printed links remain.
* Fetching a destination from the server during URL creation without SSRF controls.
* Treating a redirect service as a guarantee that destinations are safe.
* Using permanent redirect caching when disablement must take effect quickly.
* Recording unlimited raw visitor data for analytics.
* Letting analytics failure block a best-effort redirect.
* Applying owner authorization only in the web controller and not in CLI or repair tools.
* Allowing arbitrary path, query, or host input to become metric labels or log fields.

## Senior Engineer Thinking

The senior question is not “how do we turn a long URL into a short string?” It is “what makes the public identifier stable and non-enumerable, who owns the mapping, how do retries and collisions converge, how quickly can a link be disabled, and which optional analytics or abuse checks may fail without breaking the redirect contract?”

A URL shortener is a compact study of identity, caching, external input, public routing, privacy, and operational ownership. Keep code generation probabilistic but uniqueness authoritative, treat redirect behavior as a cacheable contract, and make revocation, abuse handling, and recovery part of the first design.

## Exercises

1. Choose a code length for one million, one hundred million, and one billion mappings. Estimate collision retries and explain the privacy trade-off.
2. Define an idempotent create endpoint with request fingerprinting, retention, and changed-payload behavior.
3. Design the database indexes and active-state query for redirect and owner-management paths.
4. Compare `302`, `307`, `301`, and `308` for a mapping that may be disabled or changed.
5. Design a click-event outbox with bounded retention, duplicate handling, sampling, and queue-full behavior.
6. Threat-model a preview worker that fetches destinations, including redirects, DNS changes, private networks, and response limits.

## Review Questions

* Why is random code generation not enough to guarantee uniqueness?
* What is the difference between a public code and an idempotency key?
* Why should a service not fetch a submitted destination in the create request?
* How do redirect status and cache policy affect disablement?
* Which fields belong in a mapping record and which belong in analytics?
* Why must authorization cover API, CLI, support, and repair paths?
* Which guarantees require a real database test?
* How can a hot link overload analytics while redirects remain fast?
* Why can code rollback become unsafe after mappings are published?
* What privacy and abuse policies must exist before broad public launch?

## Summary

A URL shortener is a public identity and redirect system, not merely a string encoder. Define creation, visibility, expiry, disablement, retry, analytics, and abuse contracts; validate destinations without server-side fetching; generate unpredictable codes while enforcing uniqueness in the database; make creation idempotent; separate redirect, cache, analytics, and authorization boundaries; protect the service with bounded rate limits; test races and cache invalidation; and preserve mapping semantics through rollout and recovery.
