# Chapter 252 — CAP

## Why This Matters

CAP is a model for reasoning about a distributed data system when a network partition prevents some participants from communicating. It says that a system cannot simultaneously guarantee linearizable consistency and availability for every request on both sides of an active partition while also tolerating that partition.

CAP is not a menu in which an engineer chooses two letters during architecture planning. Partitions are a failure condition, availability and consistency have precise meanings, and different operations or data stores may make different choices. The useful question is: what should this operation do when the authorities cannot communicate?

## The Three Terms

* **Consistency (C):** each operation appears to observe one current, linearizable ordering of the data.
* **Availability (A):** every request to a non-failing node receives a non-error response within a bounded time.
* **Partition tolerance (P):** the system continues to operate despite lost or delayed communication between nodes.

The CAP definition of availability is stronger than “the service is usually up,” and consistency here is narrower than every meaning of data quality. A system that returns stale data may be available but not linearizable. A system that rejects writes during a partition may preserve consistency but sacrifice availability for those writes.

## The Partition Scenario

```text
region A  ──X──  region B
  user writes         user writes
```

If both sides accept conflicting writes while communication is broken, they may return results that cannot be placed in one linearizable order. If one side refuses or redirects operations until the authority is reachable, it preserves the consistency contract for that operation but returns an error or waits.

The choice is per invariant:

```text
payment capture       → preserve one authoritative decision
product recommendation → serve stale or omit
shopping cart draft    → accept and merge, if domain permits
unique username       → reject or route to one authority
```

## CAP and Other Trade-offs

CAP does not say latency, cost, throughput, durability, or operational simplicity disappear. A consistent system may be too slow for the user contract. An available system may accept work that later conflicts. A partition-tolerant design may require reconciliation, conflict resolution, or a single write authority.

PACELC is a complementary way to discuss the normal case: when there is a partition, a system trades availability and consistency; else, it often trades latency and consistency. Use such models to expose decisions, not to label an entire product permanently.

## Choose Per Operation

Do not classify an entire application as “AP” or “CP” and stop reasoning. A service can use a strongly consistent transaction for inventory, an eventually consistent search index, and a stale-tolerant public catalog. Within one database, different tables and queries can have different isolation and freshness requirements.

Document the behavior:

```text
partition detected
  write authority unavailable → reject with retryable status
  cached catalog read         → serve data no older than 60 seconds
  permission decision         → use authority or fail closed
  analytics event             → buffer within bounded retention
```

## Authority and Quorum

A single write authority can simplify uniqueness and conflict handling but may reduce availability during its failure or partition. Quorum protocols can continue when a majority is reachable, depending on the protocol and failure model, but they add coordination, membership, and operational complexity. A quorum is not automatically linearizable; read and write rules and storage guarantees matter.

Do not implement a homemade quorum with three HTTP calls and a count. Define membership, failure detection, timeouts, duplicate requests, stale responses, and recovery. Use a storage or coordination system whose consistency contract is documented and tested.

## PHP Application Behavior

PHP code often calls a repository, cache, queue, or service client that hides the partition decision. Make the result explicit: `Unavailable`, `Stale`, `Pending`, or a valid value. Do not catch every exception and return an empty array, because that can turn a consistency or authorization failure into an apparently successful answer.

~~~php
<?php

declare(strict_types=1);

enum ReadState: string
{
    case Fresh = 'fresh';
    case Stale = 'stale';
    case Unavailable = 'unavailable';
}

final readonly class ReadResult
{
    public function __construct(
        public ReadState $state,
        public ?string $value,
    ) {
        if ($state === ReadState::Fresh && $value === null) {
            throw new InvalidArgumentException('Fresh result needs a value');
        }
    }
}
~~~

The application can choose a product response from this state instead of inferring it from a generic transport exception. Whether stale data is allowed belongs to the operation's contract.

## Testing Partitions

Test a dependency that cannot be reached, responds slowly, returns divergent versions, or recovers with queued writes. Verify consistency-sensitive writes reject or route correctly, stale-tolerant reads stay within their age bound, and buffered work does not exceed retention.

Run failure-injection tests at the network, service, database, and message layers. A test that kills one PHP process does not simulate a partition between two authorities. Test recovery and reconciliation as well as the partition interval.

## Security

Fail closed for authorization, revocation, and security-policy state unless an explicitly approved short-lived capability policy exists. Do not let a partition fallback reveal another tenant's stale data. Audit decisions made using degraded or stale state.

## Common Mistakes

* Treating CAP as a choice of two permanent product labels.
* Calling stale reads “consistent” without defining the model.
* Returning empty or affirmative data when an authority is unavailable.
* Assuming a quorum automatically guarantees linearizability.
* Ignoring latency, recovery, and conflict costs after naming a CAP choice.
* Using an application process failure as a partition test.

## Senior Engineer Thinking

Ask what a request should observe when communication is broken, who can authorize the write, and how the system converges after recovery. CAP is valuable when it turns “high availability” into an operation-level contract with explicit rejected, stale, pending, and merged outcomes.

## Exercises

1. Decide partition behavior for payments, catalog reads, permission checks, carts, and analytics events.
2. Model two regions accepting the same unique username during a partition. Choose a safe authority or conflict policy.
3. Test a stale catalog response against a 60-second freshness contract.
4. Explain why a three-node HTTP “quorum” is not enough to claim linearizability.

## Review Questions

* What kind of consistency does CAP refer to?
* What does availability mean in the CAP model?
* Why must the choice be made per operation?
* What can a system do with a write during a partition?
* Why does a quorum need more than a count of successful responses?
* Which security decisions should fail closed?

## Summary

CAP describes the unavoidable choice between linearizable consistency and availability for requests that cross a network partition. Use it to specify operation-level behavior: which writes reject, which reads may be stale, which events buffer, and which security decisions fail closed. Include latency, recovery, conflict, and operational costs, and test partitions rather than relying on architecture labels.
