# Chapter 227 — CPU

## Why This Matters

CPU time is one part of request latency and worker capacity. A CPU-heavy PHP operation can make one request slow, consume a PHP-FPM worker, and reduce throughput for unrelated requests. The right fix depends on whether the cost comes from an algorithm, database work, serialization, regular expressions, cryptography, a dependency, or contention.

Measure before changing code. Wall time identifies the user-visible cost; CPU time, samples, call counts, and allocation data help identify the cause. A faster function that causes more database queries or returns a larger response can make the system slower overall.

## Latency, Throughput, and Complexity

Latency is how long one operation takes; throughput is how many operations complete per unit of time. A request with a 20 ms CPU phase can use one worker for at least that duration, even if it spends additional time waiting on I/O. Under load, queueing can make latency grow before CPU reaches 100 percent.

State the input size and algorithmic cost. A nested loop over n items is often O(n²); replacing repeated membership scans with a set-like associative array can reduce the lookup phase to expected O(1) per item and O(n) overall, at the cost of memory.

~~~php
<?php

declare(strict_types=1);

/** @param list<string> $allowed */
function filterAllowedSlow(array $values, array $allowed): array
{
    return array_values(array_filter(
        $values,
        static fn (string $value): bool => in_array($value, $allowed, true),
    ));
}

/** @param list<string> $allowed */
function filterAllowed(array $values, array $allowed): array
{
    $set = array_fill_keys($allowed, true);

    return array_values(array_filter(
        $values,
        static fn (string $value): bool => isset($set[$value]),
    ));
}
~~~

The first version scans allowed values for each input. The second builds a lookup map once. Measure on realistic sizes; for a tiny list, the simpler first version may be adequate and easier to read.

## Find the Hot Path

Use representative load and a profiler or sampling tool to find where CPU time is spent. A single benchmark can be distorted by warmup, OPcache state, CPU frequency scaling, cache locality, or a dataset that is too small. Compare distributions and tail latency, not only the fastest run.

Instrument coarse phases such as request parsing, domain computation, serialization, and template rendering. Use sampling profilers for production-like workloads and short microbenchmarks for a narrow hypothesis. Do not add high-cardinality labels or log every loop iteration in production.

## Reduce Work Before Optimizing Instructions

The largest win often removes work:

- filter and aggregate in the database when the database owns the data;
- avoid loading fields and relationships a response does not need;
- cache deterministic expensive results with explicit freshness;
- batch repeated provider or filesystem operations;
- reject oversized or malformed input before parsing deeply;
- move CPU-heavy imports, reports, and image work to queue workers;
- choose an algorithm and data structure that fit the input scale.

Memoization is useful only when inputs repeat and cache size is bounded. A cache of a function with hidden time, locale, tenant, or authorization inputs can return incorrect data.

## PHP Runtime Considerations

PHP request workers execute user code and are recycled according to runtime configuration. OPcache can avoid repeated compilation, but it does not make an expensive algorithm cheap. JIT behavior is workload- and version-dependent; benchmark it on the target runtime and do not assume it improves I/O-bound applications.

Copy-on-write and zval behavior affect the cost of modifying shared arrays and objects. Avoid accidental copies of very large arrays, especially through transformations that materialize intermediate results. Use iterators or generators when the consumer can process values incrementally.

~~~php
<?php

declare(strict_types=1);

/** @return Generator<int, string> */
function readLines(string $path): Generator
{
    $handle = fopen($path, 'rb');
    if ($handle === false) {
        throw new RuntimeException('Cannot open input');
    }

    try {
        while (($line = fgets($handle)) !== false) {
            yield rtrim($line, "\r\n");
        }
    } finally {
        fclose($handle);
    }
}
~~~

A generator reduces peak application storage for a large file, but total CPU and I/O still exist. Check errors, encoding, and whether downstream processing is itself bounded.

## Serialization and Regular Expressions

JSON, XML, template rendering, encryption, and regular expressions can dominate CPU for large payloads. Bound request and response sizes, use the narrowest parser, and avoid catastrophic backtracking patterns. Validate input before expensive transformations and stream output when a complete in-memory representation is unnecessary.

Do not replace a clear parser with a complex regular expression simply because a microbenchmark is faster for one string. Correctness, invalid input behavior, and maintenance are part of performance engineering.

## Concurrency and Capacity

PHP-FPM workers are processes with finite CPU and memory. Increasing worker count beyond available CPU can add context switching and contention while reducing capacity for I/O-bound requests. Queue CPU-heavy tasks with a worker limit and monitor age and throughput. Protect interactive traffic from a report or import that monopolizes CPUs.

A CPU alert needs context: high utilization with low latency may be healthy; high utilization with queueing and tail latency may require capacity or less work. Compare application CPU with database, host, and dependency signals.

## Testing and Operations

Add performance tests for a bounded input and a representative large input. Assert a budget with tolerance rather than a fragile exact millisecond value. Profile before and after a change and record PHP, extension, dataset, and hardware versions. Use correctness tests for generated, cached, and streaming paths.

Monitor CPU time per route and job, p50/p95/p99 latency, worker queueing, input size, and expensive operation counts. Correlate a regression with deployment and dataset growth. A CPU optimization that changes authorization, rounding, ordering, or error behavior needs functional and security tests.

## Common Mistakes

- Optimizing a microbenchmark before finding the production hot path.
- Replacing a clear algorithm with clever code without measuring input scale.
- Materializing large intermediate arrays.
- Treating OPcache or JIT as a substitute for reducing work.
- Increasing workers until CPU contention hides the bottleneck.
- Caching a result without all tenant, time, and authorization inputs.
- Moving work to a queue without monitoring backlog and user-visible state.

## Senior Engineer Thinking

CPU performance is about useful work per request and capacity under concurrency. Measure the hot path, reduce data and algorithmic work first, use appropriate PHP structures and streaming, isolate heavy jobs, and validate both tail latency and correctness.

## Exercises

1. Measure the two filtering functions at several input sizes and explain when the map's memory cost is worthwhile.
2. Profile a report endpoint and identify work that belongs in SQL, a cache, or a queue.
3. Convert a large-file transformation to a generator pipeline and define error and cleanup behavior.
4. Set a CPU and latency budget for one HTTP route and one queue job.

## Review Questions

1. How do latency and throughput differ?
2. Why can reducing algorithmic work matter more than optimizing instructions?
3. When is memoization unsafe?
4. What does OPcache solve, and what does it not solve?
5. Why can a CPU-heavy job reduce unrelated request capacity?

## Summary

CPU performance depends on useful work, algorithmic complexity, serialization and parsing cost, and concurrent worker capacity. Measure hot paths, reduce data and repeated work, choose suitable structures, stream large inputs, isolate heavy jobs, and verify tail latency and correctness on representative environments.
