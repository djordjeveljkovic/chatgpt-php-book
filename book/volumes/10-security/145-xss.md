# Chapter 145 — XSS

## Why This Matters

Cross-site scripting (XSS) occurs when attacker-controlled text becomes executable markup or script in another user's browser. The payload may arrive through a form, database row, URL, Markdown renderer, or third-party integration. The correct defense depends on the output context.

## Context-Specific Encoding

Escape text for HTML text, HTML attributes, JavaScript strings, CSS, and URLs with the encoder for that context. Do not build JavaScript or HTML with string concatenation when a structured API or inert data element works.

```php
<?php

declare(strict_types=1);

$safeName = htmlspecialchars($displayName, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8');
echo '<p>Hello, ' . $safeName . '</p>';
```

This protects an HTML text/attribute context; it is not a universal sanitizer. Validate and sanitize rich HTML with a maintained allow-list library, or store and render plain text. A Content Security Policy can reduce impact but is a defense layer, not a reason to skip encoding.

## Stored, Reflected, and DOM XSS

Stored XSS persists in a database and reaches many users. Reflected XSS returns request data immediately. DOM XSS occurs in client-side code that inserts URL or API data into dangerous sinks such as `innerHTML` or `eval`. Test all paths, including error messages and administrative screens.

Use safe DOM APIs such as `textContent`, avoid inline script and event handlers, restrict script sources with CSP, and set cookies `HttpOnly` and `Secure` where appropriate. Do not rely on `HttpOnly` to protect all application data; an injected script can still perform actions as the victim.

## Testing and Common Mistakes

Test quotes, angle brackets, entity forms, Unicode, URLs, Markdown, JSON-in-script, and stored values. Use security scanners and browser integration tests for high-risk views. Common mistakes are double-encoding, using URL encoding in HTML, marking untrusted HTML as safe, and trusting a template auto-escape setting across all contexts.

## Senior Engineer Thinking

Treat output as a sink-specific serialization problem. Keep untrusted data typed and inert until the final context, minimize dangerous browser APIs, and make the safe template/component path the default.

## Exercises

1. Audit a template for HTML, attribute, URL, and JavaScript contexts.
2. Replace an `innerHTML` assignment with a safe DOM update.
3. Define a CSP policy and identify residual risks.

## Review Questions

1. Why is one escaping function not safe for every context?
2. How do stored and reflected XSS differ operationally?
3. What does CSP add and what does it not replace?

## Summary

Prevent XSS by encoding for the exact output context, treating rich HTML as a separate sanitized format, using safe DOM APIs, and adding CSP and cookie defenses as layers. Test stored, reflected, DOM, error, and administrative views.
