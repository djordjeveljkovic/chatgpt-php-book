# Chapter 105 — PDO

## Why This Matters

PDO, PHP Data Objects, is the standard object-oriented interface for accessing many relational database drivers. It gives application code a common connection, statement, transaction, and error API. It does not make different database engines identical, and it does not design a schema or prevent every misuse. The boundary still needs explicit configuration, ownership, failure handling, and tests.

The most reliable PDO code makes the database connection a dependency. It configures failure behavior once, uses prepared statements, defines fetch shapes, keeps transaction scopes short, and turns driver failures into useful application-level outcomes without leaking credentials or raw SQL to clients.

## Mental Model

PDO has three relevant objects:

~~~text
PDO connection
    ├── prepares SQL and begins/commits transactions
    └── creates PDOStatement objects
PDOStatement
    ├── binds or receives parameter values
    ├── executes once or repeatedly
    └── fetches rows and reports affected counts
PDOException
    └── describes a driver or database failure when exception mode is enabled
~~~

The connection is a handle to a database session. A statement is a server-facing operation associated with that connection. A transaction belongs to the connection, so the code that starts it must ensure that the same connection commits or rolls back it. Passing a connection into a repository is often clearer than making a global connection that can be silently replaced in tests.

## Constructing a Connection

The DSN identifies the driver and database location. Credentials and options are separate arguments:

~~~php
<?php

declare(strict_types=1);

function connect(string $dsn, string $username, string $password): PDO
{
    return new PDO($dsn, $username, $password, [
        PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,
        PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
        PDO::ATTR_EMULATE_PREPARES => false,
    ]);
}
~~~

Exception mode makes a failed operation visible as a throwable failure instead of requiring every call to inspect a return value. Associative fetch mode gives a stable named-column shape for simple reads. Disabling emulated prepares asks the driver to use native prepared statements when supported; the exact behavior remains driver-specific, so verify it for the selected driver and version.

Do not put credentials in source control. Read them from a secret store or process environment at the composition boundary, validate that required configuration is present, and avoid logging the resulting DSN if it can contain a password, token, or private host name. A DSN is not necessarily safe to print: some drivers include credentials or connection parameters in it.

## Driver and Portability Boundaries

PDO standardizes the PHP API, not SQL syntax, transaction isolation, data types, locking, error codes, or optimizer behavior. A MySQL DSN, PostgreSQL DSN, and SQLite DSN have different attributes. A query using PostgreSQL arrays or MySQL-specific upsert syntax is not portable merely because it is called through PDO.

Define the supported engine in deployment documentation and test that engine. If a library intentionally supports several engines, keep dialect-specific SQL in an explicit adapter and test each dialect. Avoid a lowest-common-denominator abstraction that hides important capabilities or makes errors impossible to diagnose.

## Executing a Statement

For a one-off query without values, query() is convenient. For values, prepare and execute:

~~~php
function customerExists(PDO $db, string $email): bool
{
    $statement = $db->prepare(
        'SELECT 1 FROM customers WHERE email = :email'
    );
    $statement->execute(['email' => $email]);

    return $statement->fetchColumn() !== false;
}
~~~

The false result from fetchColumn means that no row was available. Do not use a truthiness test for an arbitrary selected value: a valid first column may be zero or an empty string. Use the method whose return contract matches the query, and make the no-row case explicit in the calling code.

For a known single row, fetch one row and return a domain result:

~~~php
/** @return array{id: int, email: string}|null */
function findCustomer(PDO $db, int $id): ?array
{
    $statement = $db->prepare(
        'SELECT id, email FROM customers WHERE id = :id'
    );
    $statement->execute(['id' => $id]);
    $row = $statement->fetch(PDO::FETCH_ASSOC);

    return $row === false ? null : $row;
}
~~~

Use fetchAll only when the result is known to be small enough for the request memory budget. For large results, iterate the statement:

~~~php
function streamCustomerIds(PDO $db): Generator
{
    $statement = $db->query('SELECT id FROM customers ORDER BY id');

    while (($id = $statement->fetchColumn()) !== false) {
        yield (int) $id;
    }
}
~~~

Iteration bounds PHP-side accumulation, but rows can still remain buffered by a driver or server. Confirm the driver's buffering behavior before promising constant memory.

## Binding Types Deliberately

execute accepts values conveniently, but driver conversions can surprise code that relies on exact database types. bindValue or bindParam can declare a PDO type:

~~~php
$statement = $db->prepare(
    'UPDATE inventory SET available = available - :amount WHERE sku = :sku'
);
$statement->bindValue('amount', $amount, PDO::PARAM_INT);
$statement->bindValue('sku', $sku, PDO::PARAM_STR);
$statement->execute();
~~~

bindParam binds a variable by reference and reads its value when execute runs. bindValue binds the current value. For ordinary one-shot calls, execute with an array or bindValue is easier to reason about. PDO has no universal boolean or date parameter type; represent those according to the target schema and driver, and document the conversion.

Do not cast untrusted input merely to make an error disappear. A malformed amount becoming zero can be a business bug. Parse and validate at the input boundary, then bind the validated value.

## Transactions

Transactions are connection-scoped. A small helper can make rollback behavior hard to forget:

~~~php
/**
 * @template T
 * @param Closure(PDO): T $operation
 * @return T
 */
function inTransaction(PDO $db, Closure $operation): mixed
{
    $db->beginTransaction();

    try {
        $result = $operation($db);
        $db->commit();

        return $result;
    } catch (Throwable $exception) {
        if ($db->inTransaction()) {
            $db->rollBack();
        }

        throw $exception;
    }
}
~~~

The closure should contain the atomic database work and should not perform an HTTP call, wait for a queue, or ask a user for input. Long transactions hold locks or snapshots and make deadlocks and contention more likely. If commit fails, the application must treat the outcome carefully: the server may have committed while the client lost the response. Retrying requires an idempotency strategy, not blind repetition.

Some drivers begin transactions implicitly for certain statements or support engine-specific savepoints. PDO exposes only a portable subset. Check the driver manual and database documentation before relying on nested transactions or DDL rollback.

## Error Handling and Observability

With exception mode enabled, catch exceptions at a boundary that can choose the response or retry policy. Do not catch and ignore PDOException:

~~~php
try {
    $customer = findCustomer($db, $customerId);
} catch (PDOException $exception) {
    $logger->error('Customer lookup failed', [
        'customer_id' => $customerId,
        'sql_state' => $exception->errorInfo[0] ?? null,
    ]);

    throw new RuntimeException('Customer store unavailable', 0, $exception);
}
~~~

Log a correlation identifier, operation name, duration, and safe dimensions such as a tenant or entity ID. Avoid logging bound values that may contain passwords, personal data, or secret tokens. A SQLSTATE or driver code can help classification, but codes are not uniformly portable. Let the request layer distinguish a conflict, invalid input, missing row, transient outage, and programmer error where the driver and schema make that distinction possible.

Set connection and statement timeouts appropriate to the request budget. A PHP worker waiting indefinitely for a database can consume a process slot and make an outage spread. Timeout configuration is driver and server specific; test it under a real failure rather than assuming a PDO option has universal effect.

## Testing a PDO Repository

Keep SQL tests close to the actual engine. A test can create a temporary schema, insert fixtures, call the repository, and assert both the result and constraints. Use dependency injection to substitute a fake only when the test is about an application branch and SQL itself is already covered by integration tests.

An in-memory SQLite connection is convenient:

~~~php
$db = new PDO('sqlite::memory:', options: [
    PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,
]);
$db->exec(
    'CREATE TABLE customers (id INTEGER PRIMARY KEY, email TEXT NOT NULL UNIQUE)'
);
~~~

This tests PDO usage and simple SQL, but it does not prove behavior on PostgreSQL or MySQL. Run a separate integration suite against the production engine for locking, constraints, date behavior, JSON, generated columns, collations, and query plans.

Test rollback explicitly. Arrange an operation that fails after an earlier insert, catch the exception, then assert that neither the earlier insert nor later writes remain. Also test a second call to the same repository method: statement reuse and connection state should not leak data between calls.

## Common Mistakes

- creating a new connection for every query instead of using the request or worker lifetime deliberately;
- sharing a mutable global connection across unrelated tests;
- leaving the error mode at silent or warning behavior;
- assuming fetchColumn returns a typed integer on every driver;
- using fetchAll for an unbounded export;
- putting network calls inside a database transaction;
- catching PDOException and returning an empty result;
- assuming PDO makes vendor-specific SQL portable;
- retrying a failed commit without considering duplicate effects.

## Senior Engineer Thinking

Treat a PDO connection as a failure-prone resource with a defined lifetime and owner. Decide which layer owns transactions, which operations are safe to retry, and which errors are actionable. Make row shape and scalar conversion visible at the repository boundary. A common API is useful only when the team keeps the database-specific semantics that matter visible and tested.

## Exercises

1. Build a connection factory that reads a DSN from configuration, enables exceptions, and refuses a missing password in production mode.
2. Write repository methods for one-row, optional-row, and many-row reads. State the memory behavior of each.
3. Force a unique-key violation and classify the exception without returning raw driver text to an HTTP client.
4. Add a transaction test proving that a failure in the second statement rolls back the first.
5. Compare an in-memory SQLite test with an integration test on your production engine. List three behaviors the former cannot establish.

2. Why should a connection be injected rather than hidden in a global?

8. Why can SQLite integration tests miss production database bugs?

## Summary

PDO provides a consistent PHP interface for connections, statements, fetching, transactions, and exceptions. Configure it deliberately, prefer prepared statements, choose fetch behavior that fits the result size, bind types at the data boundary, and keep transaction scopes short. PDO does not erase SQL dialects or failure modes; production confidence comes from engine-specific integration tests and explicit retry and observability policies.
