# Chapter 137 — SSE

## Why This Matters

Server-Sent Events (SSE) is a browser-friendly way for a server to send a stream of named events over one long-lived HTTP response. It is useful for notifications, progress, and dashboards when data travels mainly from server to browser. The browser's EventSource client reconnects automatically, which makes the event ID and replay contract part of the application design.

SSE is a text protocol over the text/event-stream media type. It is not a general bidirectional channel: the client sends commands through ordinary HTTP and receives updates through the stream. When both directions need low-latency messages, compare SSE with WebSocket concepts in the next chapter.

## Event Format

An event is a sequence of UTF-8 lines terminated by a blank line. The event, id, and retry fields are optional; one or more data lines form the payload, with line breaks joined by the client. Lines beginning with a colon are comments and are useful as heartbeats.

```text
id: 1842
event: progress
data: {"job_id":"job_7","percent":80}

: keep-alive

```

Use JSON in data when the application has a structured payload, but keep the event envelope stable. An ID should be unique within the stream's replay scope. If a client reconnects with Last-Event-ID: 1842, the server needs a defined answer: replay events after 1842, start from the current position, or report that the cursor is too old.

## A Small PHP Stream

Long-lived PHP code must release the request's session lock and avoid unbounded output buffering. The exact flush behavior depends on PHP configuration and reverse proxies, so test the complete path rather than assuming that flush immediately reaches the browser.

```php
<?php

declare(strict_types=1);

header('Content-Type: text/event-stream');
header('Cache-Control: no-cache');
header('X-Accel-Buffering: no'); // recognized by nginx when applicable

session_write_close();
set_time_limit(0);

function writeSse(string $event, string $data, string|int|null $id = null): void
{
    if ($id !== null) {
        echo 'id: ' . $id . "
";
    }
    echo 'event: ' . $event . "
";
    foreach (explode("
", $data) as $line) {
        echo 'data: ' . $line . "
";
    }
    echo "
";
    if (ob_get_level() > 0) {
        ob_flush();
    }
    flush();
}

for ($i = 0; $i < 60 && !connection_aborted(); ++$i) {
    $message = findNextMessage(); // read from a bounded queue or cursor
    if ($message !== null) {
        writeSse('message', json_encode($message, JSON_THROW_ON_ERROR), $message['id']);
    } else {
        echo ": heartbeat

";
        flush();
    }
    sleep(5);
}
```

findNextMessage() is intentionally an application boundary. A database poll can work at small scale but becomes wasteful with many idle clients. A broker or publish/subscribe layer can wake a stream worker, while a durable cursor remains responsible for replay. Do not use a process-global PHP array as the queue: PHP-FPM workers are separate processes and can be recycled.

## Reconnect and Replay

The browser reconnects after a dropped connection and may send Last-Event-ID. Store a bounded event log keyed by stream and sequence. On reconnect, validate that the caller is still authorized, then replay only events visible to that caller. If the cursor has expired, send an explicit error or force a full state refresh; silently skipping updates can leave a dashboard wrong.

```js
const source = new EventSource('/events/orders', { withCredentials: true });
source.addEventListener('order.updated', (message) => {
  const order = JSON.parse(message.data);
  renderOrder(order);
});
source.onerror = () => showConnectionState('reconnecting');
```

The retry field can suggest a reconnect delay, but the server should not use it to hide an outage. Add jitter on the client or at the edge when many clients reconnect after a deploy. A stream is a subscription, so authorization changes and account deletion must invalidate it.

## Proxies, Limits, and Scaling

Configure the web server and proxy to permit streaming and avoid response buffering. Set an idle heartbeat interval shorter than the shortest intermediary idle timeout. Bound the number of concurrent streams per account and worker pool; each long-lived request consumes resources even when no events are being sent. Send a useful shutdown signal or close connections during deploy so clients reconnect to the new process.

PHP-FPM can serve SSE, but a worker remains occupied for the life of each stream. Capacity planning must include this concurrency cost. A dedicated long-running process or a gateway that owns connections can isolate stream lifetime from ordinary request workers. Shared event distribution still needs a broker or durable log when multiple application instances serve the same subscription.

## Security

EventSource supports credentials according to browser policy, but it does not let application code set arbitrary authorization headers. Cookie-authenticated streams need the same origin and CSRF reasoning as other stateful browser requests; the stream itself should not mutate state. For cross-origin streams, configure an exact Access-Control-Allow-Origin and credentials policy, and validate the Origin where appropriate.

Never place bearer tokens in a query string that will be logged. Check authorization when opening the stream and filter every event by tenant and resource. Treat event data as untrusted UI input and escape it at the rendering boundary.

## Testing and Operations

Test event framing, multiline data, IDs, heartbeats, disconnect detection, cursor replay, expired cursors, authorization changes, proxy buffering, and graceful shutdown. Use an HTTP client that exposes bytes as they arrive; a test that waits for the complete response cannot detect buffering.

Monitor active streams, bytes per stream, heartbeat failures, reconnect rate, replay lag, oldest retained event, and worker saturation. Log subscription identity and cursor, not sensitive payloads. A high reconnect rate can indicate proxy timeout, deploy behavior, browser network changes, or a server-side failure; the metric needs its cause dimension.

## Common Mistakes

- Treating SSE as a bidirectional protocol.
- Omitting event IDs and making reconnects lose data silently.
- Holding a PHP session lock for the lifetime of the stream.
- Assuming flush defeats every output buffer and proxy.
- Polling a database independently for every connected browser.
- Authorizing the initial connection but leaking another tenant's events later.

## Senior Engineer Thinking

SSE is a transport with a simple wire format, not a delivery guarantee by itself. Reliability comes from the event cursor, retention policy, authorization filter, bounded connection resources, and reconnect behavior. Design those contracts first, then choose whether PHP-FPM, a long-running worker, or a gateway can meet the expected concurrency.

3. Design authorization so a user's revoked project membership stops future events without exposing retained history.

## Summary

SSE streams UTF-8 events over a long-lived HTTP response. Use stable IDs, replay from Last-Event-ID, heartbeats, proxy-aware buffering settings, bounded connection capacity, and per-event authorization. The transport reconnects, but the application must decide what can be replayed and how to recover when history has expired.
