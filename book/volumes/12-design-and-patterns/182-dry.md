# Chapter 182 — DRY

## Why This Matters

DRY means “Don't Repeat Yourself”: every piece of knowledge should have one authoritative representation in a system. It does not mean that every similar line of code must be merged immediately. Two fragments can look alike while representing different business rules that will evolve independently.

The useful question is not “Can these lines be shortened?” It is “If this rule changes, where must a maintainer know to update it?” Duplicate knowledge causes drift; duplicate mechanics can sometimes be clearer than an abstraction that couples unrelated behavior.

## Knowledge versus Text

Consider a maximum upload size. If the value appears in PHP validation, an HTTP limit, a reverse-proxy configuration, and documentation, those are different layers that must agree. Centralize the application policy where practical, generate configuration from one source when safe, and test the boundaries that cannot be generated together.

A repeated mapping can be a sign of duplicated knowledge:

~~~php
<?php

declare(strict_types=1);

function reservationLabel(string $status): string
{
    return match ($status) {
        'pending' => 'Awaiting confirmation',
        'confirmed' => 'Confirmed',
        'cancelled' => 'Cancelled',
        default => 'Unknown',
    };
}

function reservationEmailSubject(string $status): string
{
    return match ($status) {
        'pending' => 'Reservation awaiting confirmation',
        'confirmed' => 'Reservation confirmed',
        'cancelled' => 'Reservation cancelled',
        default => 'Reservation update',
    };
}
~~~

The two functions intentionally have different wording, so merging them would couple presentation contexts. The status vocabulary itself belongs in a shared enum or domain contract; each context can then translate it for its audience.

## Centralize Domain Rules

A rule should have one owner at the layer that has enough information to enforce it. A database uniqueness constraint owns uniqueness under concurrency; a PHP validator can provide a friendly message before the write. Duplicating the database rule in PHP does not remove the constraint because two processes can pass the check simultaneously.

~~~php
<?php

declare(strict_types=1);

enum ReservationStatus: string
{
    case Pending = 'pending';
    case Confirmed = 'confirmed';
    case Cancelled = 'cancelled';
}

final class ReservationPolicy
{
    public function canCancel(ReservationStatus $status): bool
    {
        return $status === ReservationStatus::Pending
            || $status === ReservationStatus::Confirmed;
    }
}
~~~

Controllers, CLI commands, and queue consumers should call the policy rather than copy the transition table. The database should still guard invariants that must hold regardless of entry point. Tests should identify which layer owns each rule.

## Abstraction Has a Coupling Cost

A generic helper can remove syntax while hiding important differences. A “save anything” repository may accept fields it should reject, blur transactions, and make errors ambiguous. A single validation trait may couple account, invoice, and import rules that change for different reasons.

Before extracting shared code, compare:

- the business meaning and vocabulary;
- the expected future changes;
- the error and authorization contract;
- the lifecycle and transaction boundary;
- the performance and resource behavior;
- the tests needed by each caller.

If the answers differ, keep the implementations separate or share only a lower-level mechanism. Duplication is sometimes cheaper than a wrong abstraction.

## DRY Across Boundaries

Templates, schemas, OpenAPI documents, database migrations, client SDKs, and event definitions can repeat knowledge. Choose an authoritative source and define generation or compatibility checks. Generated code should be treated as an artifact and regenerated in a controlled build; manually editing generated output creates drift.

Configuration is especially easy to duplicate. A timeout might appear in an HTTP client, queue worker, proxy, and alert. These values are related but not identical: a proxy timeout must exceed an application timeout by enough margin for a useful error response. Document the relationship rather than forcing every value into one variable.

Do not share secret values merely to avoid repetition. Secret scope and ownership can require separate credentials even when they point to the same provider.

## Deliberate Duplication

Duplication can preserve isolation. A public API response mapper and an internal database mapper may contain similar fields but have different compatibility and security rules. Copying a small allow-list can be safer than a generic reflection mapper. Two tests may repeat setup because their fixtures express different scenarios; extract only stable, meaningful builders.

Mark deliberate duplication with a name or comment that explains the boundary. The goal is to prevent accidental drift, not to make line counts minimal. Revisit the decision when the requirements converge or divergence becomes costly.

## Refactoring Safely

Use tests and version control when removing repeated knowledge:

1. Identify the rule and all current representations.
2. Choose the authoritative owner.
3. Add characterization or contract tests around each boundary.
4. Introduce the shared function or generated artifact.
5. Migrate one caller at a time.
6. Delete the old copy only after coverage proves equivalence.
7. Review error, authorization, transaction, and performance changes.

A shared function has an API and a lifecycle. Keep its input and output types explicit, avoid hidden global state, and measure hot paths if the extracted code changes allocation or query behavior.

## Testing and Operations

Test that generated schemas, documentation, and clients reflect their source. Run migrations and application versions together in a compatibility matrix when a rule crosses deployments. Monitor drift such as a provider returning a field that the contract omits or a proxy enforcing a smaller limit than the application documents.

Static analysis can detect duplicated code, but a similarity report cannot decide whether two fragments share knowledge. A copy-paste warning is a prompt for design review, not an automatic refactoring command.

## Common Mistakes

- Merging similar text that has different business meaning.
- Replacing database constraints with application checks.
- Creating a generic abstraction before understanding variation.
- Sharing configuration values that have different operational roles.
- Editing generated files instead of their source.
- Removing deliberate boundary duplication and weakening security.
- Using line count as the definition of good design.

## Senior Engineer Thinking

DRY is about authoritative knowledge and controlled change. Centralize rules at the layer that can enforce them, generate or verify representations across boundaries, and keep deliberate duplication when it preserves independent contracts. An abstraction is successful when it reduces drift without coupling unrelated evolution.

## Exercises

1. Find one business rule duplicated in a controller, queue handler, and database schema. Assign ownership and add tests for each boundary.
2. Compare two similar mappers and decide whether they should share a representation or preserve a security boundary.
3. Design a source-of-truth workflow for an OpenAPI schema and generated PHP client.
4. List three configuration values that are related but should not share one variable.

## Review Questions

1. What is the difference between duplicated text and duplicated knowledge?
2. Why should a database uniqueness rule remain in the database?
3. When can duplication be safer than abstraction?
4. How should generated artifacts be kept synchronized?
5. What questions should be answered before extracting shared code?

## Summary

DRY centralizes knowledge so one change does not require remembering hidden copies. Distinguish business rules from similar text, assign ownership across PHP, databases, proxies, schemas, and generated artifacts, and keep deliberate duplication where contracts differ. Refactor with tests and review coupling, authorization, transaction, and operational effects.
