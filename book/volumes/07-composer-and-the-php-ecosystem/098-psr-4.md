# Chapter 98 — PSR-4

## Why This Matters

An application can refer to `Acme\\Billing\\Invoice` without knowing whether its source lives in `src/Invoice.php`, `lib/Billing/Invoice.php`, or a package under `vendor/`. That separation is useful only if the class name and file layout follow a shared rule. Without one, every project and every library needs private autoload configuration, and dependencies can disagree about how names become paths.

PSR-4 gives PHP projects a common mapping contract. It lets a package state which part of a namespace it owns and where the corresponding source tree begins. Composer combines those mappings into its generated loader, while other PSR-4-compatible loaders can use the same package layout. A precise understanding of the mapping makes missing-class failures easier to diagnose and avoids case-sensitive bugs that pass on one developer's machine and fail in production.

The previous chapter introduced PHP's autoload queue and Composer's loader strategies. This chapter goes deeper into PSR-4's naming and path rules; it does not repeat the SPL callback mechanics. For the full Composer command and manifest workflow, see [Chapter 92](092-composer.md) and [Chapter 94](094-composer-json.md).

## Mental Model

PSR-4 replaces a namespace prefix with a base directory, then turns the rest of the fully qualified class name into a relative path:

```text
fully qualified class name:  Acme\Billing\Report\CsvReport
configured prefix:            Acme\Billing\
base directory:               src/
remaining name:               Report\CsvReport
relative file path:           Report/CsvReport.php
candidate file:                src/Report/CsvReport.php
```

The prefix is represented by the configured base directory. It does not become extra directories beneath that base. For example, if `Acme\Billing\` maps to `src/`, the loader does not look under `src/Acme/Billing/`; it looks beneath `src/` for the part of the name after the prefix.

The mapping has three separate inputs: the symbol name requested by PHP, the namespace prefix assigned to the package, and one or more base directories. The autoloader derives candidate paths from those inputs and includes a file if it finds one. It does not create classes, download packages, or guarantee that the file contains the requested symbol. Composer's role in registering the generated loader was covered in [Chapter 97](097-autoloading.md).

## The PSR-4 Contract

PSR-4 is a PHP-FIG specification for interoperable class-file autoloading. Its normative terms such as MUST and SHOULD have the meanings described by RFC 2119. The specification uses the word “class” broadly to include classes, interfaces, traits, and other similar structures.

A fully qualified class name has a top-level namespace name, may have additional namespace components, and ends in a class name. One or more leading namespace components form the namespace prefix. That prefix maps to at least one base directory. Any namespace components after the prefix become subdirectories, and the terminating class name becomes a PHP filename by appending `.php`.

Consider the name `Acme\Billing\Report\CsvReport` and the prefix `Acme\Billing`. The remaining namespace component `Report` corresponds to a `Report/` directory, and `CsvReport` corresponds to `CsvReport.php`. With `src/` as the base, the resulting path is `src/Report/CsvReport.php`. The namespace prefix may be as short as the vendor namespace or may include a package namespace. That choice is a package's mapping policy.

The standard makes underscores ordinary characters. `File_Writer` therefore maps to `File_Writer.php`; the underscore does not introduce a directory. That differs from the older PSR-0 convention used by some legacy packages, which Chapter 97 summarized.

## Define the Mapping in Composer

Composer's `autoload.psr-4` section connects namespace prefixes to directories relative to the package root: the directory containing that package's `composer.json`. At application root, the directory is the project root. For a dependency, it is that dependency's installed package root. It is not a path relative to the `vendor/` directory as a whole.

Here is a small root-project layout:

```text
billing-app/
├── composer.json
├── src/
│   ├── Invoice.php
│   └── Report/
│       └── CsvReport.php
└── vendor/
    └── autoload.php
```

Here is a minimal root `composer.json` for the example project:

```json
{
  "name": "acme/billing-app",
  "description": "A small billing application.",
  "license": "proprietary",
  "type": "project",
  "autoload": {
    "psr-4": {
      "Acme\\Billing\\": "src/"
    }
  }
}
```

JSON represents a backslash as `\\`, so the JSON key decodes to the PHP namespace prefix `Acme\Billing\`. The trailing namespace separator is significant: every non-empty Composer PSR-4 prefix must end in `\\`, which keeps a prefix such as `Acme\Billing\` distinct from a similarly named namespace such as `Acme\BillingTools\`. Composer also allows an empty prefix as a fallback, described below. The manifest field and escaping details are covered in [Chapter 94](094-composer-json.md).

The first source file declares the matching namespace and symbol:

```php
<?php

declare(strict_types=1);

namespace Acme\Billing;

final class Invoice
{
    public function number(): string
    {
        return 'INV-2026-0042';
    }
}
```

`Acme\Billing\Invoice` has no namespace suffix after the mapped prefix, so Composer checks `src/Invoice.php`. A deeper symbol uses matching subdirectories:

```php
<?php

declare(strict_types=1);

namespace Acme\Billing\Report;

final class CsvReport
{
    public function header(): string
    {
        return 'invoice_number,total';
    }
}
```

The name `Acme\Billing\Report\CsvReport` resolves under this mapping to `src/Report/CsvReport.php`. The class name, namespace declaration, directory names, and filename should follow the same spelling and case.

After adding or changing an `autoload` mapping, regenerate Composer's loader:

```sh
composer dump-autoload
```

The application then loads Composer's bootstrap and uses the class normally:

```php
<?php

declare(strict_types=1);

require __DIR__ . '/vendor/autoload.php';

$invoice = new Acme\Billing\Invoice();
$report = new Acme\Billing\Report\CsvReport();

printf("%s: %s\n", $invoice->number(), $report->header());
```

The bootstrap registers a loader. PHP calls it when code first refers to a class-like name that is not already defined. The mapping does not eagerly include every PHP file under `src/`. This distinction is useful when reasoning about startup cost and side effects; see Chapter 97 for the loader lifecycle.

## Resolution as a Small Algorithm

A PSR-4 lookup can be understood as a sequence of candidate path calculations:

1. Receive a fully qualified class-like name.
2. Find a configured namespace prefix that covers the beginning of the name at a namespace boundary.
3. Remove the prefix from the name.
4. Replace each remaining namespace separator with the platform's directory separator.
5. Append `.php` to the terminating class name and join the result to a base directory.
6. If a candidate file exists, include it; otherwise allow the loader lookup to remain unresolved.

The namespace-boundary detail matters. A prefix `Acme\Billing\` covers `Acme\Billing\Invoice`, but it does not cover `Acme\BillingTools\Invoice`. Composer requires each non-empty PSR-4 prefix to end in the terminal separator to keep these names separate. Do not emulate namespace matching with an unbounded textual prefix check.

PSR-4 defines how a matching prefix maps to a path, but it does not prescribe precedence when a loader has overlapping prefixes. Composer's loader tries the longest matching non-empty prefix first. For that prefix, it checks the configured base directories in listed order; if no file exists, it tries a less-specific matching prefix. Only after those candidates miss does Composer check directories registered for the empty-prefix fallback. This ordering is Composer-specific behavior, not a normative PSR-4 rule; another conforming loader may make different choices when mappings overlap.

For a prefix `Acme\Billing\` mapped to `src/`, both of these requests are covered:

| Fully qualified name | Remainder | Candidate file |
| --- | --- | --- |
| `Acme\Billing\Invoice` | `Invoice` | `src/Invoice.php` |
| `Acme\Billing\Report\CsvReport` | `Report\CsvReport` | `src/Report/CsvReport.php` |

The directory names for the suffix components and the filename for the terminal class name must match their corresponding name components in case. A loader that cannot find a path should simply leave the name unresolved so another registered loader can try, as described in Chapter 97.

## Multiple Directories and Package Ownership

Composer allows a prefix to map to more than one base directory:

```json
{
  "autoload": {
    "psr-4": {
      "Acme\\Billing\\": ["src/", "generated/"]
    }
  }
}
```

This can be useful when generated code or a deliberate source split belongs to the same namespace. Each base directory is still interpreted relative to the package root, and the suffix after the prefix is interpreted in the same way for each directory. Keep ownership clear: if the same fully qualified name is declared in two candidate files, whichever file is selected first wins, and subsequent behavior can depend on that order. Duplicating class definitions across directories is a source of hard-to-diagnose bugs; prefer distinct names and one authoritative source for each class.

A Composer dependency owns its own mapping. For example, a library installed under `vendor/acme/money/` may map `Acme\Money\` to its own `src/` directory. Application classes can use another prefix and another package-root mapping. Composer combines package autoload declarations when it builds the generated loader; it does not require all code to share the application's namespace or source tree.

Composer also accepts an empty PSR-4 prefix as a fallback mapping. That is a Composer feature and not a namespace prefix conforming to the PSR-4 standard's requirement for a top-level vendor namespace. It is generally better to use a specific project or vendor prefix so that a package clearly owns the names it maps and does not become a fallback for unrelated code.

## Case Is Part of the Contract

PSR-4 requires class names to be referenced in a case-sensitive fashion, and it requires subdirectory and file casing to match the corresponding namespace and class-name components. Given:

```text
src/Report/CsvReport.php
```

the source should declare `namespace Acme\Billing\Report;` and `class CsvReport`. A request for `Acme\Billing\report\CsvReport` can lead a filesystem-based loader to check a different path, `src/report/CsvReport.php`.

PHP class-like names have historically been case-insensitive in several runtime operations, so a case error can be obscured after the intended class has already been loaded. The autoloader's path lookup still depends on the name it receives and the filesystem's case behavior. A case-insensitive development filesystem can also accept a path that a case-sensitive Linux filesystem rejects. Test class discovery in a fresh process and in an environment with the same filesystem behavior as production.

Case errors are often not caught by a JSON schema check or a PHP syntax check. The source files may all parse, and Composer may successfully generate its loader, while a later runtime lookup fails. A smoke test should ask the loader to resolve representative names with their exact production spelling.

## Lookup Misses and File Errors

PSR-4 requires an autoloader implementation not to throw exceptions or raise errors as part of its loading behavior, and says it should not return a value. An ordinary miss is not exceptional: the requested prefix may belong to another loader, or the symbol may not exist. Returning without defining the symbol allows the next callback to try. If no callback defines the symbol, PHP reports failure at the original use site.

This miss rule does not make an included source file harmless. If a candidate file has a parse error, throws during inclusion, or declares the wrong symbol, the application can still fail. These are source or package defects rather than normal “this loader does not own that namespace” outcomes. Keep loader misses quiet, and diagnose source errors from the file path and requested fully qualified name.

Do not turn user-provided input into an arbitrary class name and instantiate it just because autoloading can resolve names. Class loading executes PHP source with the process's privileges. For dynamic handlers or plugins, map external identifiers through an explicit allow-list of application-approved class names.

## Development, Build, and Runtime Boundaries

Composer's default PSR-4 lookup can discover a new source file beneath an existing mapping without rebuilding the autoloader. This supports a quick edit-run loop in development. A change to the mapping itself, such as adding a namespace prefix or changing its target directory, requires `composer dump-autoload` so the generated metadata includes the new rule.

An optimized Composer loader can build class-map entries for known source files. This moves work into the build step and can speed up lookup at runtime. Chapter 97 explains the class-map, authoritative-map, and APCu trade-offs in detail. When using an optimization, generate the loader from the same source tree that will be deployed, and test it after generation. An authoritative map in particular assumes classes are known at build time; runtime-generated classes or files added later need deliberate support.

The package mapping is also a deployment contract. If an application moves `src/` or packages ship a different directory layout without updating metadata, class names that worked locally may disappear after install. The `vendor/` tree and generated loader should be installed or built from the package versions and source tree selected for that release; see [Chapter 95](095-composer-lock.md) for the lock-file boundary.

## A Practical Verification Loop

For the example project, keep the verification sequence small and exercise the real generated loader:

```sh
composer validate --strict
composer dump-autoload
php -l src/Invoice.php
php -l src/Report/CsvReport.php
php -r 'require "vendor/autoload.php"; $i = new Acme\Billing\Invoice(); if ($i->number() !== "INV-2026-0042") { exit(1); } echo "autoload ok\n";'
```

The inline command checks the exact namespace-to-path mapping, includes the Composer bootstrap, and uses a public method to prove the expected file declared the class. A dedicated test is easier to maintain for a larger project, but this smoke check is valuable during initial setup or release diagnostics.

Tests should cover more than the happy path:

- Load a class at the mapped prefix's root and one at a nested namespace.
- Add a source file beneath an existing mapping without regenerating metadata, then confirm default PSR-4 discovers it.
- Add or change a prefix, regenerate the loader, and verify the new mapping.
- Request a name that belongs to another namespace and confirm this mapping does not claim it.
- Check class, namespace, directory, and file casing in a fresh PHP process on a case-sensitive filesystem.
- If production enables optimized or authoritative autoloading, run the same smoke tests against the optimized generated files.
- Exercise a package after installation into `vendor/` so relative paths are checked from the package root, not only from a working tree.

Composer's `validate` command checks manifest validity, and `dump-autoload` generates loader files; neither proves every declared class path and source declaration match. Runtime loading is the meaningful behavior test. When a class is missing, inspect the exact requested name, the active prefix, package root, suffix path, and letter case before changing the configuration.

## Common Mistakes

- Including the full namespace prefix in the mapped directory tree, for example putting `Acme/Billing/Invoice.php` below `src/` even though `Acme\Billing\` already maps to `src/`.
- Omitting the terminating namespace separator from a non-empty Composer PSR-4 key and accidentally matching a similarly named namespace.
- Treating underscores as directory separators under PSR-4.
- Using the repository root as a mapping base when the `composer.json` that declares the mapping belongs to an installed dependency.
- Naming a PHP file differently from its terminal class name or using different letter case in a subdirectory.
- Expecting `composer validate` or `composer dump-autoload` to discover a class whose namespace and path do not match.
- Regenerating autoload metadata for every new class, even though a file under an existing PSR-4 mapping is found dynamically by Composer's default loader.
- Relying on case-insensitive development behavior, or on a class already loaded with a different spelling, to validate a fresh lookup.
- Depending on two base directories to declare the same class and silently shadow each other.
- Using an empty Composer prefix without understanding that it is a broad Composer fallback rather than a normal PSR-4 vendor namespace mapping.

## Exercises

1. Create the `Acme\Billing\` mapping above. Add `src/Invoice.php` and `src/Report/CsvReport.php`, generate the autoloader, and load both classes from a separate entry point.
2. Add `src/Report/JsonReport.php` under the existing mapping after generating Composer's loader. Verify that the default PSR-4 loader finds it. Then add a second namespace mapping and determine which step requires regeneration.
3. Rename `src/Report/` to `src/report/` and test in a clean process on a case-sensitive filesystem. Restore the expected case and document how the failing name and candidate path differ.
4. Map one namespace prefix to two directories. Put distinct classes in each directory and test them. Then put the same class in both and observe why duplicate ownership is unsafe; remove the duplicate.
5. Install a small local package with its own `composer.json` and PSR-4 mapping into a consuming project. Confirm that its base path is resolved relative to the package's root.
6. Generate an optimized autoloader in a disposable project, add a class afterward, and compare default optimized lookup with authoritative class-map behavior. Explain when rebuilding is required.

## Review Questions

1. What does PSR-4 replace when converting a fully qualified class name into a file path?
2. If `Acme\Billing\` maps to `src/`, where should `Acme\Billing\Report\CsvReport` be declared?
3. Why does a Composer PSR-4 key end with a namespace separator, and how does JSON escaping affect the written key?
4. What does PSR-4 say about underscores, alphabetic case, and path casing?
5. Which directory is the base for a mapping declared by an installed dependency?
6. Why should a PSR-4 loader treat an unresolved name as a normal miss rather than throwing?
7. When does Composer need `dump-autoload` after source or mapping changes?
8. Why should case-sensitive autoload behavior be tested in a fresh process and on a production-like filesystem?
9. What risks arise when two base directories or packages can provide the same fully qualified class name?
10. Why is an autoload mapping not an authorization mechanism for dynamically chosen classes?

## Summary

PSR-4 standardizes the path lookup for class-like names. A namespace prefix maps to one or more base directories; namespace components after that prefix become subdirectories, and the terminal class name becomes a `.php` filename. Underscores are ordinary characters. Name references, subdirectories, and filenames must preserve the case required by the specification.

Composer declares mappings under `autoload.psr-4`, with paths relative to the package root. Every non-empty Composer prefix must end with a namespace separator, represented as `\\` in JSON; Composer's empty-prefix fallback is an extension. Composer's loader searches the longest matching non-empty prefix first, then shorter prefixes and finally the empty-prefix fallback. Once a prefix exists, new files beneath it are found by the default loader without rebuilding metadata; changing the mapping requires `composer dump-autoload`. Validate the real path behavior by loading representative classes, including on a case-sensitive production-like filesystem. Treat lookup misses as normal, keep namespace ownership clear, and do not use autoloading to authorize untrusted class names.
